# Design — XML 042 Fase 1

Data: 2026-03-19
Escopo: geracao isolada de XML 042 por poco e por dia, usando os dados diarios subsea ja curados no `mpfm_app`.

## Objetivo

Adicionar um modulo isolado de `XML 042` para emitir um arquivo por `poco + dia`, sem misturar o fluxo com exportacoes MPFM/SEP existentes.

A Fase 1 cobre:

- cadastro mestre de pocos elegiveis para 042
- localizacao dos candidatos diarios subsea
- previa para revisao humana
- geracao do XML 042 final no padrao ANP
- armazenamento do documento emitido e trilha de auditoria minima

Ficam fora desta fase:

- validacao de XML externo
- importacao/regeneracao de XML FCS320
- comparacao end-to-end completa

## Regras de negocio

### Unidade de emissao

- um XML por `poco + dia`
- a chave operacional do documento e `production_day + cod_cadastro_poco`

### Elegibilidade

So pode haver emissao quando existir correspondencia unica entre:

- `well_operator_name` do dado diario
- `subsea_tag` do dado diario
- registro ativo e habilitado em `well_catalog_042`

Se houver ambiguidade, ausencia de cadastro ou poco desabilitado, o sistema nao gera automaticamente.

### Fonte dos valores

A geracao usa apenas os dados diarios subsea ja existentes no banco da aplicacao.

Mapeamento da Fase 1:

- `MED_POTENCIAL_OLEO` <- potencial diario de oleo em `Sm3/d`
- `MED_POTENCIAL_GAS` <- potencial diario de gas em `Sm3/d`, dividido por `1000`
- `MED_POTENCIAL_AGUA` <- potencial diario de agua em `Sm3/d`

### Regras de formato

- encoding: `ISO-8859-1`
- decimal com virgula
- sem separador de milhar
- nome do arquivo: `042_<CNPJ8>_<AAAAMMDDHHmmSS>.xml`
- ordem fixa dos nos em `TESTE_POCO`:
  1. `COD_CADASTRO_POCO`
  2. `IND_TIPO_TESTE`
  3. `DHA_TESTE`
  4. `DHA_APLICACAO`
  5. `IND_VALIDO`
  6. `MED_POTENCIAL_OLEO`
  7. `MED_POTENCIAL_GAS`
  8. `MED_POTENCIAL_AGUA`
  9. `LISTA_SEPARADOR`

## Arquitetura

O modulo sera isolado das rotas e servicos atuais:

- `repositories/xml042/`
- `services/xml042/`
- `routes/xml042_routes.py`
- `static/app.xml042.js`

Responsabilidades:

- repositorio:
  - CRUD do catalogo mestre
  - persistencia de candidatos curados
  - persistencia de documentos emitidos
- servico de curadoria:
  - localizar os candidatos subsea do dia
  - cruzar com o catalogo
  - classificar o status de QA
- servico de serializacao:
  - formatar os valores para ANP
  - montar o XML final
  - gravar arquivo e hash
- rotas:
  - listar candidatos
  - aprovar/revogar aprovacao
  - gerar XML
  - baixar XML
  - listar historico

Nao deve haver acoplamento direto com `export_routes.py`.

## Fluxo funcional

### 1. Listagem de candidatos

Para o dia selecionado:

1. ler os dados diarios subsea
2. identificar `well_operator_name` e `subsea_tag`
3. cruzar com `well_catalog_042`
4. calcular os potenciais curados
5. classificar a linha:
   - `elegivel`
   - `sem cadastro`
   - `cadastro ambiguo`
   - `desabilitado`
   - `valor critico ausente`

### 2. Revisao humana

A tela exibe uma grade com:

- dia
- banco
- poco operacional
- tag subsea
- codigo do poco ANP
- oleo
- gas bruto
- gas convertido / 1000
- agua
- status QA
- aprovacao

O usuario aprova explicitamente a linha antes da emissao.

### 3. Geracao do XML

Para uma linha aprovada:

1. montar o payload final
2. serializar no formato ANP
3. gravar em disco
4. registrar em `xml042_documents`
5. disponibilizar download

## Tela nova

Nova aba: `XML 042`

Blocos:

1. filtros
   - mes
   - dia
   - banco
   - poco
   - status

2. grade de candidatos
   - linhas diarias elegiveis
   - status QA
   - botao de aprovar
   - botao de gerar XML

3. painel lateral ou inferior de previa
   - XML pronto
   - memorial dos valores
   - nome do arquivo

4. historico
   - xmls emitidos no periodo

## Tratamento de erro

Bloquear geracao quando:

- nao houver match unico no catalogo
- `cod_cadastro_poco` estiver vazio
- `oil/gas/water` criticos vierem ausentes
- o poco estiver `active = 0` ou `enabled_042 = 0`

Erros operacionais devem ser mostrados com causa objetiva e sem stack trace.

## Decisoes

### Decisao 1 — modulo isolado

Pros:

- reduz risco de regressao
- facilita manutencao
- prepara bem a Fase 2

Cons:

- adiciona novos arquivos e tabelas

Escolha: modulo isolado.

### Decisao 2 — um XML por poco e por dia

Pros:

- aderencia direta ao requisito operacional confirmado
- simplifica rastreabilidade

Cons:

- aumenta o numero de arquivos emitidos

Escolha: um XML por poco e por dia.

### Decisao 3 — usar dados diarios ja curados

Pros:

- reaproveita a base atual da aplicacao
- evita parser PDF novo nesta fase

Cons:

- depende de mapear corretamente quais metricas diarias equivalem ao PRD

Escolha: usar os dados diarios curados e manter o parser PDF para fases futuras apenas se necessario.
