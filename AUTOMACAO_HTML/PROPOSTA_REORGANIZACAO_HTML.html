Objetivo da proposta

Transformar a página em um painel técnico de exceção e decisão, em vez de apresentar simultaneamente todos os dados disponíveis. A proposta utiliza somente elementos já existentes, sem exigir novas fontes.

O relatório deve responder, nessa ordem:

1Qual período e escopo estou analisando?
2Os dados são confiáveis e suficientemente completos?
3Quanto foi medido?
4Há desvios que exigem atenção?
5Quais pontos explicam o resultado?
6Onde consulto a evidência detalhada?

Para a versão simplificada, a melhor abordagem é transformar a página em um painel técnico de exceção e decisão, em vez de tentar apresentar simultaneamente todos os dados disponíveis.

O objetivo seria responder, nessa ordem:

  • Qual período e escopo estou analisando?
  • Os dados são confiáveis e suficientemente completos?
  • Quanto foi medido?
  • Há desvios que exigem atenção?
  • Quais pontos explicam o resultado?
  • Onde consulto a evidência detalhada?

A proposta abaixo utiliza somente elementos e informações que a página já possui, sem exigir novas fontes.

1. Princípios para a nova organização

1.1. Uma página, três níveis

A página deve ter apenas três níveis de informação:

Nível 1 — Situação geral

Resposta rápida para decisão:

  • período analisado;
  • escopo;
  • qualidade do conjunto de dados;
  • produção consolidada;
  • quantidade de desvios;
  • situação executiva.

Nível 2 — Diagnóstico técnico

Resposta para engenharia:

  • valores por fase;
  • cobertura;
  • comparações físicas;
  • desvios mais relevantes;
  • evolução temporal;
  • contribuição por ponto.

Nível 3 — Evidência

Resposta para investigação:

  • tabela detalhada filtrável;
  • registros usados no consolidado;
  • campos para XML;
  • auditoria e rastreabilidade.

A simplificação não deve remover os dados técnicos, mas alterar sua prioridade visual.

3. Cabeçalho

O cabeçalho deve ser curto e permanecer visível durante a rolagem.

Conteúdo recomendado

Relatório de Monitoramento Multifásico
Período analisado: 12/08/2026 00:00 a 13/08/2026 23:00
Última geração do relatório: DD/MM/AAAA HH:MM

À direita:

[Atualizar] [Exportar] [Auditoria]

Ajuste importante

O relatório deve distinguir claramente:

  • período analisado;
  • último registro disponível;
  • data de geração do HTML.

Essas três datas não devem ser apresentadas como se fossem equivalentes.

4. Filtros organizados em uma única faixa

Atualmente, os filtros ocupam um papel importante, mas podem ser consolidados em uma faixa horizontal e recolhível.

Linha principal

De [12/08/2026] até [13/08/2026]  Granularidade [Horária]
Tipo [Topside]  Ponto [Todos]  Par físico [Todos]

Linha secundária

Variável principal [Massa total corrigida]
Comparação [HC corrigida]
Busca [________________]

Ações

[Aplicar filtros] [Limpar] [Mostrar somente exceções]

Regras de usabilidade

  • exibir filtros ativos como etiquetas;
  • manter o período sempre visível;
  • indicar quantos registros permanecem após o filtro;
  • aplicar o mesmo filtro a todos os componentes;
  • impedir que uma seção use outro período silenciosamente.

Exemplo de contexto ativo:

Período: 12–13/08/2026 · Horário · Topside · 214 registros · 5 pontos

8. Evolução temporal e ranking

Esses dois componentes são complementares e podem ocupar a mesma seção.

Layout sugerido

┌────────────────────────────────────┬───────────────────────────┐
│ Evolução no período                │ Contribuição por ponto    │
│ gráfico temporal                   │ ranking horizontal        │
└────────────────────────────────────┴───────────────────────────┘

Evolução temporal

Manter inicialmente:

  • uma variável principal;
  • uma variável comparativa;
  • até três pontos selecionados.

Controles:

Variável 1 [Total corrigido]
Variável 2 [HC corrigido]
Pontos [P2] [P4] [P5]

Elementos visuais recomendados

  • linha contínua para total;
  • linha tracejada para HC;
  • cor fixa por ponto;
  • lacunas reais quando não houver dados;
  • marcadores para eventos relevantes;
  • tooltip com data, hora, valor, unidade e qualidade;
  • zoom temporal.

Valores ausentes não devem ser conectados por uma linha contínua, pois isso sugere existência de medição.

Ranking

Manter apenas uma variável por vez:

Ranking por massa total corrigida — último dia do filtro

Antes dos valores, mostrar claramente a referência:

Data de referência: 13/08/2026

10. Área de alertas e eventos

O Pareto é útil, mas deve ficar depois das exceções de medição.

Estrutura

ALARMES E EVENTOS
2

Críticos: 141
Falhas: 143
Comunicação: 61
Desvios: 39

Abaixo, o Pareto.

Melhoria conceitual

A página deve diferenciar:

  • ocorrência;
  • registro afetado;
  • evento único;
  • flag;
  • categoria.

Como flags múltiplas podem aparecer no mesmo registro, incluir uma observação fixa:

Um registro pode contribuir para mais de uma categoria.
O total de ocorrências não representa necessariamente o total de registros afetados.

Dados para conferência e preparação do reporte.

Evitaria declarar automaticamente que o XML está aprovado sem validação formal.

12. Hierarquia visual sugerida

Cores

Utilizar cores com significado fixo:

  • verde: conforme;
  • amarelo: atenção;
  • vermelho: crítico;
  • cinza: sem dado ou não aplicável;
  • azul: informação ou navegação.

Não usar cores diferentes apenas como decoração.

Tipografia

Três níveis principais:

Título da página
Título de seção
Valor/KPI e texto auxiliar

Evitar muitos tamanhos de fonte e excesso de texto em caixa alta.

Espaçamento

  • maior distância entre seções;
  • menor distância entre elementos pertencentes ao mesmo card;
  • alinhamento consistente dos números;
  • unidades visualmente secundárias;
  • números tabulares para facilitar comparação.

13. Navegação simplificada

A navegação atual pode ser reduzida para cinco áreas:

Visão geral
Comparações
Tendências
Registros
Auditoria/XML

Correspondência proposta:

  • Visão geral: filtros, status, produção e qualidade;
  • Comparações: Subsea × Topside e separador;
  • Tendências: gráficos, ranking, alarmes e eventos;
  • Registros: tabela detalhada;
  • Auditoria/XML: evidências, validação final e reporte.

A separação por conteúdo técnico continua existindo, mas com menos opções concorrentes no topo.

14. Regras gerais indispensáveis

Mesmo em uma versão simplificada, estas regras devem ser preservadas.

Regra 1 — Um filtro global

Todos os componentes devem usar o mesmo contexto:

período
granularidade
tipo
ponto
par físico

Se algum bloco não respeitar o filtro, deve declarar isso explicitamente.

Regra 2 — Ausência não é zero

Usar estados distintos:

Sem dado
Zero medido
Não aplicável
Dado inválido
Dado excluído

Regra 3 — Cobertura não é qualidade

Manter indicadores separados:

Cobertura temporal
Completude
Qualidade PI
Validade técnica

Regra 4 — Fórmulas visíveis e verificáveis

Sempre apresentar:

HC = óleo + gás
Total = óleo + gás + água
GOR = gás padrão / óleo padrão

Se o valor for proveniente diretamente de uma tag e não calculado, indicar:

Valor reportado pela fonte

Regra 5 — Exceções antes dos detalhes

A ordem deve ser:

status → desvio → impacto → tendência → evidência

Regra 6 — Contexto em todos os resultados

Todo KPI ou comparação deve carregar:

  • período;
  • origem;
  • unidade;
  • condição de referência;
  • método;
  • status.

15. Resultado final esperado

A versão simplificada deve permitir que o usuário compreenda a situação em três etapas.

Em poucos segundos

Qual é o período?
Qual é o status?
Quanto foi medido?
Existe algum desvio crítico?

Em aproximadamente um minuto

Qual ponto causou o desvio?
A cobertura é adequada?
Quais fases contribuíram?
O comportamento é pontual ou persistente?

Na investigação técnica

Quais registros compõem o valor?
Quais tags e bancos foram utilizados?
Qual fórmula foi aplicada?
Qual dado foi ausente ou excluído?
Quais valores serão utilizados no reporte?

Conclusão

A proposta não reduz a profundidade técnica do relatório. Ela reorganiza a informação para que o usuário veja primeiro:

contexto → confiabilidade → produção → exceções → tendências → evidências

Os dados completos continuam disponíveis, mas deixam de competir visualmente com os indicadores necessários à tomada de decisão.

A principal mudança seria transformar o HTML de uma página extensa de exposição de dados em uma interface técnica progressiva, na qual o detalhe aparece conforme a necessidade. Isso preserva o rigor metrológico, melhora a leitura operacional e reduz o risco de conclusões baseadas em blocos fora de contexto.
